# 初步项目评审与改进（2026-10-21）

## 结论

已经基本完成“实验室设备预约与资源调度平台”的核心目标，适合作为后端主项目。当前最有价值的是把事务边界、候补公平和恢复证据讲清楚，再争取少量真实试用；继续增加技术组件并不是优先项。

这次判断来自源码、迁移、现有测试和重新执行的验证。2026-10-19 的双实例、故障恢复和浏览器报告是仓库历史证据，本轮没有把它们当成重新执行的结果。

## 本轮修复：统一时间输入语义

原 `UtcJsonConfig` 仅给输出添加 UTC `Z`，输入仍交给默认 `LocalDateTime` 处理。新增回归测试证实：客户端以 `2026-10-15T10:00:00+08:00` 提交时，无法按预期得到对应的 `02:00Z` 预约响应。日程查询也没有统一偏移归一规则。

现在 JSON 请求与 MVC 查询参数共享同一解析规则：有偏移则按同一时刻转换到 UTC，无偏移保持历史 UTC 约定。预约、改期、维修输入共用该类型配置。不同偏移表达的同一时段共用时隙与幂等结果，非法偏移、数值时间戳返回400。

新增2项集成测试覆盖 HTTP 创建、等价时刻重放、偏移查询、另一用户冲突候补及非法输入不落库。原有47项业务测试继续保留。

## 后续优先级与验收标准

1. **真实反馈，优先于新功能。** 找3～5位同学完成设备查找、冲突候补、审批和取消任务，记录完成率、卡点与修复前后差异。没有实际试用就不要写“已服务某实验室”。
2. **让恢复证据可持续复现。** 将已有双实例/恢复脚本接入手动 CI 工作流，固定数据库版本、请求规模、故障点和不变量查询，保存当次报告。重点验证终态无残留时隙、无重复通知、候补顺序正确。
3. **只选一个真实业务扩展。** 根据试用反馈在培训有效期、营业日历或多设备预约中选择一个；若选多设备，按设备ID排序加锁、整笔事务回滚并验证死锁重试边界。
4. **部署前治理。** 账号管理、HTTPS、数据库备份恢复和数据保留。它们比为简历引入 Redis/MQ/微服务更直接。

## 简历建议

可用标题：**实验室设备预约与资源调度平台**。

建议重点表述三件事：以数据库时隙约束和统一锁顺序保证并发分配；以持久化期限和条件更新实现公平候补及可重复调度；以事务 Outbox/Inbox、失败隔离和恢复测试支撑站内通知可靠性。

本轮可准确写“同一套49项集成测试在H2和MySQL8.4通过”。负载数字必须同时写环境、时长、请求类型与错误率；不能把30秒样本写成生产容量。对于学生简历，理解并亲自演示上述设计，比罗列更多接口更有说服力。

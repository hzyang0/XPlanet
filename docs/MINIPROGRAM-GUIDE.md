# 微信小程序：入门、联调与发布边界

## 1. 目前是什么版本

原项目是响应式 Web 应用：电脑和手机浏览器均可访问，不是 Windows 桌面程序。新增 `miniprogram/` 是微信原生小程序源码，使用 WXML/WXSS/JavaScript，通过 `wx.request` 访问相同的 Spring Boot 后端。没有复制预约数据库或实现第二套候补算法。

它已经具备用户侧主流程：账号注册／登录 → 搜索设备 → 查询某天占用时段 → 提交预约／进入候补 → 确认补位 → 签到 → 结束使用；同时支持取消、已确认预约改期、通知分页和已读。管理员仍在网页端进行培训授权、审批、维护封锁和运营处理。小程序不是已经发布的微信线上应用。

## 2. 本地启动（第一次约 15 分钟）

1. 安装 JDK 17+，按照根 README 构建后端；有 Maven 时在仓库根执行 `mvn -f xplanet-booking/pom.xml clean verify`。
2. 执行 `java -jar xplanet-booking/target/xplanet-booking-2.0.0.jar --spring.profiles.active=demo`。在浏览器访问 `http://127.0.0.1:8080`，确认可以登录。demo 配置才创建演示账号，不要用在公开环境。
3. 安装微信开发者工具，选择“导入项目”，目录选本仓库 `miniprogram`。配置中的 `touristappid` 用于游客联调；如工具要求 AppID，换成自己的测试号／小程序 AppID，不能使用别人的 AppID。游客模式权限以当前微信工具为准。
4. 在本地开发设置中临时关闭“校验合法域名、web-view 域名、TLS 版本及 HTTPS 证书”。这只用于电脑模拟器的 `http://127.0.0.1:8080` 联调，不是发布配置。
5. 小程序登录页填上述服务地址，使用 `alice / password123` 或自行注册模拟账号。密码只在提交时使用，不落盘；登录 token 存储在小程序本地。
6. 管理员在网页给模拟用户授予所需设备培训资格。如果想先走简单流程，新建“不要求审批、不要求培训”的模拟设备。

真机的 `127.0.0.1` 指向手机自身。手机预览应使用微信允许的 HTTPS 测试域名，并确保后端可达；局域网调试是否允许 HTTP 取决于工具与调试方式。不要把电脑模拟器成功当成手机网络已经通了。

## 3. 两位模拟用户的演示脚本

先创建独立模拟设备，避免污染真实预约。预约时间设为明天整点至下一整点。

| 步骤 | 操作 | 预期 |
| --- | --- | --- |
| 1 | 用户 A 预约该时间段 | 已确认 |
| 2 | 退出登录，用户 B 预约相同时段 | 候补中；不等于已获得设备 |
| 3 | 用户 A 取消 | 服务端释放占用并向 B 发出限时补位 |
| 4 | 用户 B 刷新预约记录 | 待确认补位，显示截止时间 |
| 5 | B 点击确认补位 | 普通设备已确认；需审批设备进入待审批 |
| 6 | B 改期 | 成功后旧预约取消，新预约生效；冲突则旧预约保留 |
| 7 | 在开始前 10 分钟至开始后 15 分钟内签到 | 使用中；设备前一预约仍在有效使用期时拒绝 |
| 8 | 结束使用 | 已完成，释放占用，推进候补 |

通知是数据库站内通知，需刷新；尚未接入微信订阅消息。不要依赖后台自动弹窗提醒来保证不漏补位。

## 4. 源码阅读顺序

- `app.json`：页面注册和底部导航。
- `utils/api.js`：服务地址、Bearer token、统一错误、401 清理、会话切换隔离、预约幂等键。
- `utils/time.js`：手机本地日期／时间与带 Z 的 UTC 请求转换；状态标签。
- `pages/login`：平台账号登录与注册；尚未使用 `wx.login`。
- `pages/equipment`：设备搜索和分页。
- `pages/book`：当天占用查询、预约和改期；失败草稿恢复。
- `pages/reservations`：列表、补位、取消、签到与完成。
- `pages/inbox`：站内通知。
- 后端 `ApiController → BookingService → Store`：所有权限、资格、时间和并发约束都在服务器检查。

日期选择器展示本地时间。例如中国时区 09:30 会发送 `01:30:00Z`。服务器存储 UTC。不要对 `toISOString()` 的结果再次手动减 8 小时。

占用表显示的是每个已占用的 30 分钟槽；空白不是预约承诺。打开页面后其他人可能抢先提交，只有预约接口返回的状态是最终结果。

## 5. 网络失败为什么不能立即换一个请求标识

服务器可能已经提交事务，只是响应丢失。如果重试时生成新标识，会被视为另一笔操作。客户端按“服务地址 + 登录身份 + 路径 + 请求体”保存一个草稿与请求键；同样内容重试复用原键，服务端返回原预约。改动内容后才换键。切换账号或服务器清除草稿，防止跨身份混用。

当前仅保留最近一个预约／改期草稿。创建多个交错草稿再返回旧操作时，先查询预约记录确认状态，避免用户主动重复提交。取消、签到等状态动作由后端实现幂等状态检查。网络错误时不会自动重试写请求。

收到旧账号发出的迟到响应时，客户端拒绝展示。401 清理本地 token 并返回登录页。退出时尝试撤销服务端会话；网络失败下本地仍退出，服务端 token 需要等待到期，因此共享设备应确保退出请求成功。

## 6. 自动验证与人工验收

在仓库根运行（Node.js 18+）：

```sh
node --test miniprogram/tests/client.test.cjs
TZ=Asia/Shanghai node --test miniprogram/tests/client.test.cjs
RUN_MINI_LIVE=true node miniprogram/tests/live-flow.cjs
```

最后一条需要本地 demo 后端，会注册两个带随机后缀的模拟用户、新建模拟设备，验证权限拒绝、幂等重试、冲突候补、取消补位、确认与改期，结束后取消预约并停用模拟设备。测试账号及审计记录会保留，可在一次性演示数据库中运行。自定义地址用 `BOOKING_URL`，管理员密码用 `BOOKING_ADMIN_PASSWORD`。

Node 测试覆盖公共逻辑和控制器加载，不编译 WXML，也不代表微信运行时兼容认证。开发者工具和真机仍必须检查：页面布局、中文输入、日期选择器、跨日／时区、弱网、后台恢复、两账号切换、合法域名与证书、授权提示、补位过期、管理员权限、读屏和小屏文字。

## 7. 真实发布还需要什么

- 自有微信小程序 AppID、符合要求的主体／备案／隐私说明及审核材料。
- 自有 HTTPS 后端域名、可信证书、微信后台 request 合法域名配置，后端生产数据库和备份。
- 关闭 demo 种子，替换默认管理员密码，配置访问频率限制、日志脱敏和监控。
- 如接入微信登录：前端只发送 `wx.login` code，后端保管 AppSecret，调用微信换取身份，再做本平台账号绑定。客户端不得存 AppSecret；不能把客户端传来的 openid 当作可信身份。
- 如接入订阅消息：由用户主动授权，服务端将通知事件转换为模板消息，处理授权拒绝、限额、发送失败和去重。站内信仍是事实来源。

## 8. 面试如何讲

可以说：“我增加了原生微信小程序客户端，复用同一套预约事务和状态机；客户端专门处理 UTC、重复提交、弱网结果不确定和身份切换，使用模拟用户完成了接口联调。”

如果尚未在微信工具、真机和线上审核完成，不要说“已经上线并服务真实实验室”。真正的设计重点是多客户端仍共享同一份服务端约束，以及弱网下如何查询与重试，而不是页面数量。

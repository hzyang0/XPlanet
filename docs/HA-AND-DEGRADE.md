# 高可用边界与演进方向

> 这份文档说明：当前项目保持单机中间件和单服务实例的可复现形态，同时列出有真实部署需求时的演进路径。
>
> **核心立场**：当前规模单机够用，只有在可用性目标、容量数据或动态实例治理需求出现后，才引入相应集群与治理组件。

---

## 一、当前形态(有意为之的简单)

- 应用：Gateway / article / interaction / user / AI / Agent 各单实例
- Redis：单机
- MySQL：单机
- RocketMQ：单 NameServer + 单 Broker

这是当前可复现实验环境的合理形态：能完整跑通核心能力，同时避免引入尚无验证目标的运维复杂度。

---

## 二、各组件的高可用演进路径

### 2.1 应用层：多实例 + 负载均衡
- 现状：每个服务单实例，Gateway 是唯一外部入口，Agent 只接受内部调用；
- 演进：每个服务部署多实例，由 Gateway、容器平台或云负载均衡分发流量；
- 关键点：**业务事实不能只放在应用内存**。点赞关系、Outbox、待投影增量、AI 任务和 checkpoint 都持久化在 MySQL，应用实例不持有不可恢复的待处理事实。本地缓存 L1 通过 MQ 广播失效，并用短 TTL 兜底；
- 点赞待发送事件和待投影增量都持久化在 MySQL；Outbox 用租约抢占，投影用 `SKIP LOCKED` 分批并发处理。

### 2.2 Redis:哨兵 / Cluster
- 现状:单机 Redis
- 演进:
  - **哨兵(Sentinel)模式**:1 主 N 从 + 哨兵监控,主挂自动故障转移。适合中等规模。
  - **Cluster 模式**:数据分片到多节点,容量和吞吐都能扩。适合大规模。
- 代码影响:很小。Redisson 和 Spring Data Redis 都支持配置哨兵/集群地址,业务代码不用改。
- 注意:Cluster 下要注意热点 key 倾斜(单个热 key 仍落单节点),这正是本项目用**本地缓存 L1**
  额外兜热点的原因——Cluster 解决不了单热点,L1 能。

### 2.3 MySQL:主从 + 读写分离
- 现状:单机
- 演进:主从复制,写主库、读从库分担读压力;再大可分库分表
- 代码影响:读写分离可通过中间件(ShardingSphere)或多数据源实现
- 注意:主从有复制延迟,读从库可能读到旧数据,要评估业务能否容忍

### 2.4 RocketMQ:多 master + 主从
- 现状:单 namesrv + 单 broker
- 演进:namesrv 多节点(无状态,挂一个不影响);broker 多 master 多 slave,master 挂了 slave 顶上
- 消息可靠性:同步刷盘 + 主从同步复制(本项目用异步,生产按需调强)

## 三、当前已实现的故障隔离与恢复

高可用不只是增加实例，还包括隔离非核心依赖、保存可恢复状态，以及为失败设置明确边界。当前实现包括：

### 3.1 user 服务降级(UserClient)
- 文章渲染需要作者名,要调 user 服务。
- user 服务挂了怎么办?**不抛异常,返回兜底名"用户N"**,文章照常展示。
- 原理:依赖隔离——非核心依赖(显示作者名)的故障,不应拖垮核心功能(看文章)。
- 还加了本地缓存(5分钟),既提性能又减少对 user 服务的依赖频率。

### 3.2 点赞服务降级(LikeService)
- 点赞关系和 Outbox 在同一个 MySQL 本地事务中；数据库失败时整体回滚，不会只改状态却丢事件。
- RocketMQ 暂时不可用不阻塞点赞事务，relay 保留 Outbox 并按指数退避重试。
- 点赞主链不把 Redis 作为事实源；Redis 故障会影响缓存、限流或进度等能力，但不会改变 MySQL 中已经提交的点赞关系。

### 3.3 缓存重建降级(ArticleCacheManager)
- 缓存击穿重建时抢不到分布式锁,不无限等待,**降级直接查库**。
- 理由:可用性优先,不能让请求因为抢不到锁而无限阻塞。

> 降级的统一思想:**分清核心与非核心,非核心故障要隔离,不能级联拖垮核心链路。**
> 这是微服务容错的基础原则。

## 四、如何说明当前高可用边界

当前项目完成的是**可恢复的单实例闭环**，不是已经部署好的生产高可用集群：

1. 应用状态尽量外置：业务事实、Outbox、投影增量和 checkpoint 均持久化，本地 L1 只承担可丢弃缓存；
2. 依赖失败有边界：User 查询可降级，MQ 失败由 Outbox 恢复，缓存重建抢锁失败可直接回源；
3. 中间件仍是单节点：Redis Sentinel/Cluster、MySQL 主从、RocketMQ 多 Broker 要在出现可用性目标后按需引入；
4. 扩容前仍需补齐负载均衡、完整 Trace 上下文、积压告警、容量压测和故障演练，不能把“可水平扩展的代码结构”等同于“已经高可用”。

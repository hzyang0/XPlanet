# 当前项目评估与后续路线

## 是否适合作为秋招后端项目

适合。当前已经形成设备查询、资格校验、预约与审批、候补限时确认、签到与回收、维修停机、原子改期和通知管理的完整闭环。它能够支撑对事务、锁、索引、状态机、幂等、调度及故障恢复的深入讨论。

面试重点应放在设计依据和测试证据。未在学校实际部署或没有真实同学试用记录时，不要写成学校正式上线系统，也不能承诺能通过所有面试。

## 四个核心亮点

1. **时段排他与配额一致性。** 半小时时隙主键 `(equipment_id,slot_at)` 统一保护预约和维修。创建先锁用户行再锁设备行，原子检查跨设备50条活跃配额；其他路径不反向加用户锁。同设备请求串行化，是明确的吞吐取舍。
2. **候补公平与可恢复状态机。** 较早重叠候补不被后来短预约绕过；资格确认、审批、取消与过期在设备锁内重读状态并条件更新。期限持久化，进程重启后可以恢复维护；按游标分页扫描，批量读取占用和资格，合并阻塞区间以降低候补比较成本。
3. **原子改期与维修日历。** 维修和预约使用同一个时隙主键空间；冲突拒绝且不静默取消预约。改期在同一事务取消原单、创建关联新单并记录幂等关系，失败整笔回滚，审批设备重新审批。
4. **事务 Outbox 与故障隔离。** 业务、审计、Outbox 同事务；逐事件事务写Inbox和确认。失败指数退避，五次后隔离；管理员可以查看积压和失败、审计人工重试，避免单条坏消息阻塞正常通知。

## 仍然需要准确表达的边界

- 一次预约一台设备，半小时对齐；不支持任意分钟区间、多设备原子预约。
- 维修日历已实现，工作日营业时间、节假日规则尚未实现。
- 改期仅支持本人已确认且未开始的同设备预约，不支持修改正在使用的设备或静默迁移候补。
- Outbox 是同库站内通知，不是跨MQ投递。技术栈不要写未接入的Redis、RocketMQ、Nacos或Feign。
- 登录限制为每实例辅助限制；公开部署还需HTTPS、正式账号管理和集群级注册/登录防护。
- 资格目前为授予/撤销，尚无培训申请和资格到期流程。
- 本次有短时双实例负载样本，没有长时间稳定性、极限容量或真实学校用户试用报告。
- 历史记录、审计和已投递事件还需要按真实使用规模制定保留、归档和备份策略。
- 软件预约到期不等同于设备物理停止，未接硬件控制。

## 简历表述参考

技术栈：Java 17、Spring Boot、Spring Security、Spring JDBC、MySQL、Flyway、JUnit、Docker。

项目描述：面向实验室单件设备的预约与资源调度平台，提供培训准入、审批、候补限时确认、签到回收、维修日历和原子改期，重点解决时段排他、状态竞争和任务故障恢复。

核心技术可用四条：

1. 以半小时时隙主键统一约束预约与维修占用，结合用户行和设备行的统一锁顺序，保证并发配额检查和资源分配一致。
2. 实现预约状态机与公平候补递补，基于持久化截止时间、分页维护和条件更新，处理审批、取消、确认及超时之间的竞争。
3. 采用事务内原子改期与关联新单，保留原申请审计，目标冲突或写入失败时回滚；维修与预约竞争复用数据库时隙排他约束。
4. 采用Outbox与Inbox单事件事务保证站内通知可恢复，补充退避、失败隔离及管理员审计重试；通过H2/MySQL集成测试、双实例并发和重启恢复验证关键不变量。

## 高频追问

**为什么不只查询时间重叠？** 两个事务可能同时查到空；设备行锁保护判断和候补决策，时隙主键提供最终排他。

**为什么需要用户锁？** 设备锁只约束单设备，不能保护跨设备的用户总配额或跨设备复用的幂等键。统一锁顺序减少死锁风险。

**审批中和OFFERED是否占位？** 是，否则等待确认/审批期间时段可能被别人占用；相应代价由截止时间和超时释放控制。

**为什么改期创建新单？** 原申请参数和审计保持不变，原始创建请求仍可重放；新时段可以重新审批，取消旧单和创建新单在同一事务回滚。

**坏消息如何处理？** 单事件事务失败后记录退避，达到五次隔离，不挡后续事件；修复原因后由管理员审计重试。外部MQ还需另做接收方幂等。

**多实例调度是否只执行一次？** 不追求只调用一次，依靠数据库锁、最新状态和条件更新，使重复维护不会重复分配或释放。

**两组负载说明什么？** 在本机两个实例共享MySQL的限定场景中，单设备锁竞争更明显；结果不代表生产最大吞吐。具体环境和请求类型见原始JSON。

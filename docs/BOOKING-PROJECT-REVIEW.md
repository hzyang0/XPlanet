# 实验设备预约平台：代码评估、优化顺序与面试准备

评估日期：2026-10-19。依据是 `XPlanet-Booking-Final.zip` 中的预约源码、附带验证记录，以及本次本机复验。本报告将已经实现的能力和建议分开；建议不代表代码已经具备。

## 1. 是否适合作为硕士秋招的后端项目

适合，现有范围已足以支撑一个完整的后端项目。我的判断依据是业务和代码：预约、审批、培训门槛、候补、公平性、限时确认、签到、释放与通知构成了一条闭环；竞争发生在时间段、状态和用户资格之间，能够引出事务、索引、锁、幂等和恢复的深入讨论。

它的价值取决于能否解释设计并用证据验证。功能数量、微服务数量或技术栈长度不能代替这些。没有对接真实实验室、没有真实试用反馈时，应称为可部署的预约平台原型，不能写成学校正式上线系统。

作为“一个 Java 后端项目 + 一个独立 Agent 项目”的组合，职责也比较清晰：本项目展示关系建模、并发控制、状态一致性和可靠调度；Agent 项目展示工具编排、证据与模型应用。

目前最需要的是补强验证和少量关键规则，而非继续增加大量外围功能。

## 2. 实现清单与原设想的差异

| 原设想或面试说法 | 现有实现 | 准确说法 |
| --- | --- | --- |
| 时间区间预约 | 起止必须对齐半小时，0.5～8 小时，未来 30 天内 | 半小时离散时隙，使用左闭右开区间 `[start,end)` |
| 任意分钟的区间排他 | 未实现 | 不可写成任意连续区间预约 |
| 多设备同时预约 | 一次请求只接受一个 equipmentId | 未实现多资源原子预约 |
| 修改预约、调整时段 | 有创建、取消、确认、审批、签到、完成 | 当前没有改期接口 |
| 两种并发算法对比 | 设备行锁与时隙主键协同使用 | 当前是一个方案的两层保护，没有实现 A/B 性能对照 |
| 候补队列 | 按预约 ID 顺序，保护重叠的较早候补 | 设备内入库顺序，不代表客户端发送时间绝对 FIFO |
| 培训与审批 | 布尔资格、固定审批流程 | 尚无资格到期、培训申请、审批流编辑 |
| Outbox 与消息 | 同库 event_outbox → inbox_notification | 已实现持久化站内通知；没有接外部 MQ、短信或邮件 |
| 多实例 | 共享数据库行锁、持久化期限和调度 | 应使用 MySQL/MariaDB；H2 文件是单实例体验 |
| Redis、分布式锁、Feign | 预约模块未使用 | 不应把旧社区/秒杀技术写进本项目技术栈 |
| “35 项测试”和并发数据 | 包内附带 H2/MariaDB 云端记录 | 本机复验与附带历史记录分开描述，详见验证文档 |

## 3. 四个可以深入展开的亮点

### 3.1 时隙唯一约束与设备级并发控制

入口为 `ApiController.create`，核心在 `BookingService.create`、`Store.equipment`、`Store.allocate` 和 Flyway 建表脚本。

一次 14:00～16:00 预约对应 14:00、14:30、15:00、15:30 四个时隙。`reservation_slot` 的主键 `(equipment_id,slot_at)` 使同设备同时隙无法被两条预约占用。16:00～17:00 与前一条相邻，不会冲突。

写操作先取得设备行 `SELECT ... FOR UPDATE`，锁后重读预约，随后检查资格、冲突和候补，再改变状态。设备锁负责把“判断、选择、分配”串成一致的决策；唯一主键负责最终排他。事务隔离级别为 READ_COMMITTED，以便等待锁后读取最新已提交数据。

面试必须解释的取舍：同设备写请求会串行化，包括不相交的时间段；不同设备通常可以并行。此方案适合实验室资源规模，不能据此宣称高吞吐或无锁。JVM 内的 synchronized 无法保护另一个实例，而数据库锁可以。

### 3.2 候补与限时资格状态机

核心在 `BookingService.maintain`、`accept`、`cancel`、`decide`、`Models.Status`。

候补没有立即占时隙；补位时先分配时隙，再转换为 OFFERED，两者同事务。OFFERED 和 PENDING_APPROVAL 都持有时隙，否则确认和审批等待期间可能被其他人抢占。确认期限取“当前时间 + 10 分钟”和预约开始时间的较早者。

公平策略是：较早的长预约如果因某个时段被占而等待，后来的重叠短预约不能绕过；不重叠的预约仍可分配。这样减少长预约饥饿，但可能降低设备利用率，需要能解释为什么按场景选择该策略。

所有确认、取消、审批、过期都使用同一设备锁和状态条件更新。迟到审批不能把 CANCELLED 恢复为 CONFIRMED；重复取消不能释放下一位候补的时隙。

### 3.3 基于持久化期限的可恢复调度

核心在 `Maintenance.tick`、`BookingService.sweep/maintain`、`reservation.deadline`。

数据库保存状态和截止时间。后台每轮扫描、逐设备在独立事务中处理审批超时、候补过期、未签到回收和使用完成。崩溃后重新扫描，不依赖进程内定时器还记得之前的任务。

两实例同时扫同设备会竞争同一行锁，锁后检查最新状态，已处理的状态不会重复推进。这是可重复执行的调度，并不是“定时任务只执行一次”。默认 5 秒是扫描间隔，不是保证 5 秒内完成；数据库等待和扫描工作量都会增加延迟。

### 3.4 业务审计与持久化通知

核心在 `Store.audit` 和 `OutboxDispatcher.dispatch`。

预约状态、时隙、审计、Outbox 在同一业务事务内提交。投递事务中锁定待投递事件、写 Inbox 并写 delivered_at；失败整体回滚。Inbox 的 event_id 唯一，防止同事件重复生成站内信。

必须讲清楚：这是同一个数据库内的异步物化。无需推导成跨数据库或跨 MQ 的“恰好一次”。将来若发邮件或 MQ，发送结果不能与本库状态原子提交，还需要稳定 eventId、至少一次投递、接收方幂等、重试和死信。

追问“为什么不直接写 Inbox”：完全可以在业务事务中直接写 Inbox，代码更简单。当前 Outbox 的收益是将通知生成与预约主事务分离，并留下可重试的待投递记录；代价是额外轮询和短暂通知延迟。没有外部发送需求时，不必声称它是唯一正确方案。

## 4. 代码检查发现的风险与优化顺序

以下是静态阅读发现的风险或扩展边界，未在本轮批量修改业务逻辑。现有 35 项测试通过也不能证明这些边界已被覆盖。

### 第一优先级：先补针对性测试和一致性缺口

**1. 用户全局 50 条活跃预约上限存在并发竞态。**

`BookingService.create` 在设备锁内执行 COUNT 后 INSERT。同用户并发预约不同设备时，两个事务锁的是不同设备，都可能看到 49 条，随后各插一条，超过上限。此问题不破坏时隙唯一性，但会违反用户配额。

建议：如果 50 是硬限制，在创建路径先取得用户/配额行锁，再取得设备锁；所有需要同时持有两类锁的路径统一锁顺序。或者使用事务内配额计数器的条件更新。先新增“两设备、同用户、接近上限”的并发回归用例，再选方案。

**2. 幂等键的跨设备竞争需要明确客户端语义。**

同设备重复请求在设备锁下可返回原记录；相同 `(userId,requestKey)` 被用于不同设备时，可能并行执行并由唯一约束拒绝其中一个，最终没有重复记录，但响应可能是通用 409。建议增加跨设备复用同键测试，并明确同键不同参数始终冲突；客户端网络重试必须保留原键和原参数。

**3. 严格限制查询时间范围。**

`ApiController.schedule` 使用 `Duration.toHours() > 168`，不足一小时会被截断，因此 7 天多几十分钟可能被接受。建议直接用 Duration 比较 7 天，并覆盖恰好 7 天、超 1 秒、起止相同和反向区间。风险是边界不精确，不是预约超卖。

**4. 时间格式应显式携带 UTC 偏移。**

当前 API 使用没有 Z 的 LocalDateTime 并约定 UTC，前端会转换，文档也有说明；其他客户端可能误传本地时间。后续可用 Instant/OffsetDateTime 对外返回 `...Z`，通过版本化契约升级；不要直接改数据库时间类型而忽视数据迁移。

**另一个已在本机复现的问题：异常映射不完整。**

登录后请求 `GET /api/equipment/1/schedule`，省略必填 from/to，实际得到 500；浏览器自动访问不存在的 `/favicon.ico` 也得到 500。`ApiErrors` 的通用 Exception 处理器将这些框架错误覆盖成服务器失败。建议为缺少必填参数、请求方式错误和不存在资源保留相应的 400/405/404，补充 HTTP 回归测试，并提供 favicon。该问题影响接口契约、日志和监控，但不是预约并发排他失效；本轮仅记录，未改变交付模块逻辑。

### 第二优先级：调度规模与运行可观测性

**5. 调度全表扫描与候补算法的增长成本。**

`Maintenance.tick` 每轮取所有设备 ID，再逐设备扫描所有活跃预约；`maintain` 的 blocked 列表逐个比较重叠，较长候补队列可能出现平方级比较；每次 slotsFree、trained 还有单独 SQL。建议先测少量热点设备和大量空闲设备的差异，记录 SQL 数、锁等待与补位延迟，再增加分页、待处理设备筛选、期限索引查询和候补长度限制。不要一开始换成另一套复杂调度框架。

**6. Outbox 批次竞争和坏消息隔离。**

当前一次锁住最多 100 个事件并在一个事务投递。多实例会等待同一批；一条异常事件可能让整批回滚，并持续阻塞后面的消息。对当前小型同库通知可接受，增长后应选择短事务、可领取批次、重试计数/失败原因和隔离失败事件；数据库支持时可评估 SKIP LOCKED。配合积压数量、最老事件年龄和失败次数告警。

**7. 现有指标尚未形成运维入口。**

代码注册了维护失败数、投递失败数、待投递量等 Micrometer 指标，但配置只开放 health，安全配置也不会自动允许访问 metrics。已有指标对象不等于已经具备监控。可通过管理员接口展示关键指标，或提供鉴权保护的管理端点；指标至少覆盖锁等待、补位延迟、Outbox 最老事件年龄和调度耗时。

### 第三优先级：正式试用前的基础治理

- 登录限制是每实例内存计数；注册没有同等限制。正式试用前增加网关/反向代理限流、注册控制、HTTPS 和密码找回/账号管理。
- 每次鉴权查询数据库，支持撤销且实现简单；压测后再评估会话查询成本，不必默认改成 JWT。
- 预约、审计和通知会持续增长，应明确保留期、归档和备份恢复；不能随意清空作为设备停用操作。
- 审批规则目前是设备布尔开关，并无规则编辑接口和规则版本快照。不要写成“动态规则引擎”。
- 软件自动完成不能证明设备物理停止；超时占用、设备故障、管理员强制处理需要产品规则和现场管理配合。

## 5. 真正值得新增的功能

建议按需求只做下面一至两个，并各自包含测试、页面、迁移与文档。

| 功能 | 为什么值得做 | 验收要求 |
| --- | --- | --- |
| 设备可用日历与维修停机时段 | 实验室有营业时间、检修和节假日，当前全天开放不够贴近实际 | 预约和维修并发不得重复占用；明确维修是否取消已有预约、由谁通知；日历对用户可见 |
| 原子改期 | 很常见，而且能讲清“释放旧时段、申请新时段”的事务边界 | 新时段失败保留原预约；同键重放可重试；审批/候补规则明确；与取消竞争有回归测试 |
| 培训申请与资格有效期 | 将管理员手动授予拓展为真实流程 | 到期后的未来预约和正在使用分开处理；管理员操作审计完整 |
| 多设备原子预约（可选进阶） | 联合实验确有同时使用多设备的需求 | 按设备 ID 顺序加锁；全成功或全回滚；不做“部分预约成功”；组合候补另行设计 |

优先选择“日历/维修”补业务真实性；想进一步展示并发深度，可选“原子改期”。多设备会显著增加队列公平和锁顺序复杂度，不必作为当前投递简历的前置条件。

不建议优先加入商城、支付、聊天、推荐、积分或 AI。这些功能与设备预约核心关系较弱。也无需仅为列技术栈而拆 Gateway/Nacos/微服务、加入 Redis 分布式锁、Kafka/RocketMQ；若后续确有跨服务通知或独立扩容需求，再引入对应组件并验证。

## 6. 比加功能更有价值的验证

### 6.1 持续负载和锁竞争测试

包内“32 用户、2 实例，1 确认/31 候补”和 50 用户集成测试证明一个并发场景的正确性。它们不是稳定性测试，也不能外推生产 QPS。

在独立 MySQL/MariaDB 测试库中分别测：

1. 多用户抢同设备同时间：主测排他和排队，不只看 HTTP 200。
2. 同设备不同时间：观察设备行锁导致的串行化。
3. 多设备分散流量：与热点设备场景比较锁竞争。
4. 取消、候补确认、审批与扫描混合：主测状态机。
5. 逐步增加负载并持续运行，记录 CPU、连接池、错误比例、P50/P95/P99、扫描延迟和数据库锁等待。

每轮检查时隙没有重复、终态没有时隙、持有状态时隙数量与区间一致、通知没有重复、Outbox 积压可排空。压测工具不能把 WAITLISTED 都当作预约成功。

### 6.2 故障恢复与真实试用

复现强制终止后审批过期、候补递补、通知恢复；补数据库连接短断和长期积压场景。仅在隔离环境执行。

邀请少量同学按“查设备—预约—审批—签到—取消—候补确认”试用，记录日期、人数、任务完成率、困惑点和修复记录。没有用过真实设备时，只称为试用反馈，不称为实地投入使用。

## 7. 简历可以这样写

技术栈：Java 17、Spring Boot、Spring Security、Spring JDBC、MySQL/MariaDB、Flyway、JUnit、Docker。
H2 可放在测试/演示环境说明，不必突出为业务数据库；Docker 只有配置、未实际运行时应在面试中讲清验证边界。

项目描述：面向实验室单件设备的预约与调度平台，提供资格校验、审批、候补限时确认、签到回收及状态审计，重点解决时段冲突、状态竞争和进程故障后的任务恢复。

四个核心技术点：

1. **时段排他与并发控制：**以半小时时隙建模预约区间，结合设备级行锁与 `(equipment_id,slot_at)` 主键约束防止重复占用，事务内完成预约、时隙和审计写入。
2. **候补公平与状态机：**实现按入库顺序的候补递补和限时确认，保护较早的重叠候补；通过锁后重读与状态条件更新处理取消、审批、确认及过期之间的竞争。
3. **可恢复任务与通知：**持久化业务期限，支持重复扫描恢复超时任务；以本地事务 Outbox 和 eventId 唯一约束实现站内通知幂等投递。
4. **权限与验证：**实现培训资格、角色和预约归属校验、可撤销随机 Token 会话；使用数据库集成测试验证并发冲突、幂等重放、事务回滚与状态边界。

双实例和数据库数字仅在保留相应报告、能解释运行方式时补入。不要把云端交付记录改写成自己在本机测得的结果。

## 8. 面试中最需要准备的追问

| 问题 | 回答方向 |
| --- | --- |
| 为什么不用一条“时间重叠查询”就结束？ | 并发下两个事务可能都查到空，需要锁保护决策和数据库约束最终排他 |
| 行锁和唯一主键是不是重复？ | 锁维持候补与状态决策的一致；主键兜底时隙排他，职责不同 |
| 没有预约时怎么加锁？ | 锁已存在的 equipment 行，不依赖预约记录是否存在 |
| 为什么不用 Redis 锁？ | 全部事实在同一数据库，本地事务可覆盖；Redis 锁不能替代时隙唯一约束 |
| 为什么使用 READ_COMMITTED？ | 获锁后重读最新已提交状态；仍依赖写路径锁协议和条件更新，隔离级别不是全部保证 |
| OFFERED 是否占时段？ | 是，表示限时保留，否则确认时资格可能已被别人占用 |
| 为什么审批中也占位？ | 为审批结果预留资源，但可能降低利用率，故有审批截止时间 |
| 长候补会不会饿死？ | 后来重叠请求不绕过早期候补，代价是部分空闲区间暂时无法利用 |
| 多实例任务重复执行怎么办？ | 持久化状态/期限、设备行锁、条件更新和事务保护，不追求进程只执行一次 |
| 消息是否恰好一次？ | 当前同库 Inbox+确认事务具有原子边界；外部发送需按至少一次设计 |
| 机器时间不一致怎么办？ | 当前 Clock/UTC 约定需配合时间同步；正式多实例可评估数据库时间或统一时间源 |
| 哪里是瓶颈？ | 热点设备串行锁、活跃预约扫描、候补重叠比较、每请求会话查库；先测量再优化 |
| 设备已在使用却自动完成，真的停止了吗？ | 软件预约完成与物理设备控制不同，目前没有硬件联动 |
| 你遇到过什么问题？ | 用能复现的例子：取消/审批竞争、重复释放、UTC 偏移、通知回滚；区分亲自修复和继承的交付记录 |

建议亲手走完一次演示并选择一个真实问题复现、修复、补测试，这比把所有类名背下来更能支撑深入追问。

## 9. 后续实施顺序

1. 保持当前可运行基线，先补用户配额、幂等键跨设备和查询边界的针对性测试，再修复相应缺口。
2. 在固定 MySQL/MariaDB 环境跑持续负载，补数据库状态一致性与故障报告。
3. 按实际反馈添加“可用日历/维修时段”或“原子改期”其中一个模块。
4. 完善扫描分页、Outbox 失败隔离和受保护的运行指标。
5. 邀请少量用户试用，依据真实反馈决定是否继续扩展。

完成前两步后，项目已具备更扎实的秋招讨论材料。是否继续加业务，取决于时间、岗位要求和真实需求。

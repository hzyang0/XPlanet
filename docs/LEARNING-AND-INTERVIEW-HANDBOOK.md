## 1. 先建立正确的项目地图

### 1.1 用一句话定义问题

面向实验室单件设备，协调**谁有资格、什么时间能用、是否需要审批、冲突时谁先候补、取消和超时后怎样恢复资源**。

这不是一个只会减库存的系统。库存是设备与时间的组合：同一设备14:00—16:00和15:00—17:00冲突，16:00—17:00与前者相邻但不冲突。培训资格、审批和候补会改变资源分配决策。

### 1.2 当前实际技术栈

| 技术 | 实际职责 | 不要扩大成什么 |
| --- | --- | --- |
| Java17+、Spring Boot3.5 | 应用、HTTP、事务与调度 | 不是微服务集群 |
| Spring JDBC、MySQL/H2 | SQL、行锁、约束、事务 | 不使用JPA，也没有Redis分布式锁 |
| Spring Security、BCrypt | 身份与角色校验、密码哈希 | 不使用JWT或学校统一认证 |
| Flyway | V1/V2/V3迁移和校验 | 不应手改已执行迁移 |
| Outbox/Inbox | 同库站内通知 | 没有接MQ、短信和邮件 |
| Micrometer、Actuator | 运行指标、健康检查 | 不等于已建成完整监控告警平台 |
| JUnit、Docker、Python脚本 | 回归、数据库和HTTP验证 | 不等于生产用户或无限吞吐证明 |
| 原生HTML/CSS/JS | 用户与管理员工作台 | 不需要Node前端构建 |

所有Java文件在 `xplanet-booking/src/main/java/com/xplanet/booking/` 下。

| 顺序 | 文件 | 阅读时必须回答的问题 |

## 2. 三种学习节奏

### 两小时：获得可讲述的骨架

| 时间 | 动作 | 验收 |
| --- | --- | --- |
| 0～20分钟 | 启动demo，创建、取消一次预约 | 说清用户与管理员路径 |
| 20～45分钟 | 读Models、迁移、create | 画出用户锁→设备锁→时隙→审计/事件 |
| 45～70分钟 | 用两个账号争同一时段，再取消首单 | 解释WAITLISTED与OFFERED区别 |
| 70～95分钟 | 读maintain与通知事务 | 能讲重复调度和崩溃后的处理 |
| 95～120分钟 | 跑测试，练习第14章的90秒介绍 | 回答5个关键追问并指出源码 |

### 一天：能处理主要追问

上午完成业务流程、数据模型、锁和幂等；下午逐个推演候补、审批、改期、Outbox失败；晚上完成演示脚本与一次不看资料的自测。至少亲手制造一次409、一次403、一次候补晋升、一次改期失败后原单保持不变。

### 七天：形成自己的项目理解

1. 第1天：运行与产品规则，画架构和状态机。
2. 第2天：事务、索引、隔离级别、用户配额与幂等。
3. 第3天：候补公平、限时确认、多实例竞争。
4. 第4天：审批、培训、维修和原子改期。
5. 第5天：Outbox、失败隔离、重启恢复和排障。
6. 第6天：复现测试/负载，解释性能结果与局限。
7. 第7天：录制8分钟演示，模拟面试，整理自己确实完成的修改和证据。

不需要七天都写新功能。能解释“为什么这样设计、什么会失效、替代方案成本是什么”更重要。

## 3. 从启动到第一次演示

### 3.1 本地启动

```bash
cd xplanet-booking
./mvnw clean verify
java -jar target/xplanet-booking-2.0.0.jar --spring.profiles.active=demo
```

Windows使用 `mvnw.cmd`，或根目录 `START-WINDOWS.bat`。已有Maven可在仓库根目录执行 `mvn verify`。云开发环境可先 `source /workspace/.setup/activate.sh`，Maven代理/缓存参数见已保存的环境说明；这些是云环境要求，不是项目自身依赖。

demo用户 `alice/password123`，管理员 `admin/admin12345`，仅用于本地体验。默认H2文件为启动工作目录的 `data/booking.mv.db`；要在相同目录重启，否则可能创建另一份数据库。H2文件模式只用于单实例。

### 3.2 八分钟演示顺序

1. 普通用户查找设备、查看时段，提交未来半小时边界上的预约。
2. 第二个普通用户提交相同时段，展示候补状态。
3. 首用户取消，第二个用户得到限时确认资格；确认后变成已确认或待审批。
4. 管理员审批需要审批的设备；普通用户尝试管理接口应403。
5. 演示需要培训的设备：无资格拒绝，管理员授予后可以申请。
6. 演示原子改期：有冲突的目标拒绝，原单不变；无冲突目标创建关联新单。
7. 管理员创建维修时段，用户无法占用同一时隙。
8. 查看审计、通知和管理员运行概览，解释失败事件重试入口。

签到窗口与开始时间有关，现场不必等待数小时。用测试中的MutableClock展示签到/超时边界；不要为了演示直接改正式数据或关闭业务校验。

### 3.3 不背URL，追踪一个请求

登录 `POST /api/auth/login` 得到token；后续带 `Authorization: Bearer ...`。创建预约 `POST /api/reservations` 的关键字段是设备ID、起止时间、用途和requestKey。完整接口及示例见 [API文档](BOOKING-API.md)。

建议在 `ApiController.create`、`BookingService.create`、`Store.allocate`、`Store.audit` 打断点。观察同一个请求如何写入reservation、reservation_slot、reservation_audit和event_outbox。

## 4. 数据模型与核心不变量

### 4.1 先掌握不变量，再记表名

1. 同一 `(equipment_id, slot_at)` 最多有一个占用者。
2. 时隙行必须且只能属于一个预约或一个维修块。
3. 占位状态持有对应时隙；终态不应残留时隙。
4. 同用户同requestKey只对应一条创建结果，同键异参数不能被当作重试。
5. 业务状态变更、审计与Outbox一起成功或一起回滚。
6. 一个Outbox事件最多生成一条Inbox通知。
7. 迟到的审批、取消、调度不能将终态重新激活。
8. 当前单个用户活跃预约/候补最多50条，并发跨设备也不能绕过。

数据库约束守住一部分不变量，其余由锁内业务判断、事务和测试共同保证。不要说“有唯一索引，所以所有业务都正确”。

### 4.2 表的职责

| 表 | 核心字段/约束 | 作用 |
| --- | --- | --- |
| app_user | username唯一、角色 | 用户和管理员 |
| auth_session | token_hash主键、expires_at | 可撤销会话，数据库不存原token |
| equipment | enabled、approval_required、training_required、version | 资源与准入配置 |
| qualification | 用户+设备联合主键 | 设备培训资格 |
| reservation | 用户+request_key唯一、状态/起止/期限 | 业务申请与状态 |
| reservation_slot | 设备+slot_at主键、预约/维修二选一 | 最终时间排他 |
| reservation_audit | 原状态、新状态、操作者、原因 | 业务追溯 |
| event_outbox | delivered_at、retry_count、next_attempt_at、failed_at | 待投递事件与失败管理 |
| inbox_notification | event_id唯一 | 用户站内通知 |
| event_retry_audit | event_id、actor_id | 管理员手动重试审计 |
| equipment_block/equipment_audit | 时段、active、请求键、变更原因 | 维修停机及设备操作追溯 |
| reservation_reschedule | 原单、替代单、请求键、目标时间 | 改期幂等关联 |

V1创建预约基础模型，V2扩展Outbox重试控制，V3加入维修/改期。已应用的迁移不能随意改内容，否则Flyway校验失败；新需求应增加新迁移。

## 5. 一次预约请求逐层追踪

以用户A预约设备E的14:00—16:00为例。这里的时间统一按UTC存储；页面可以显示本地时间。

```text
HTTP认证/DTO校验
  -> 进入BookingService事务（READ_COMMITTED）
  -> 锁用户A行
  -> 查同用户requestKey，存在则校验参数并返回原结果
  -> 锁设备E行
  -> 校验时间、设备启用、培训资格
  -> maintain(E)：清理到期状态、尝试补位
  -> 拒绝维修冲突、本人重叠申请、超出50条活跃配额
  -> 检查前序重叠候补和时隙空闲
  -> 插入CONFIRMED / PENDING_APPROVAL / WAITLISTED
  -> 占位状态分配时隙
  -> 写审计与Outbox
  -> 提交事务并返回
```

14:00—16:00占4个槽：14:00、14:30、15:00、15:30。区间是 `[start,end)`，结束时刻不占槽，所以16:00开始的新预约可以相邻。

这里“不成功分配”通常不是系统异常：正常竞争会进入候补；没有培训资格是403；重复键修改参数是409；非法时间是400。面试时先区分业务结果和技术失败。

## 6. 状态机与边界时间

| 状态 | 占槽 | 如何进入/离开 |
| --- | --- | --- |
| WAITLISTED | 否 | 有冲突或前序重叠候补；可补位→OFFERED，开始时间已到→EXPIRED |
| OFFERED | 是 | 候补获资格；用户确认→已确认/待审批；期限到→EXPIRED |
| PENDING_APPROVAL | 是 | 需审批；批准→CONFIRMED，拒绝→REJECTED，期限到→EXPIRED |
| CONFIRMED | 是 | 可签到→IN_USE，未签到超期→NO_SHOW，可取消/改期 |
| IN_USE | 是 | 主动结束或到期→COMPLETED；不支持普通取消 |
| COMPLETED/CANCELLED/REJECTED/EXPIRED/NO_SHOW | 否 | 终态，不允许被迟到操作恢复 |

默认规则：半小时对齐、0.5～8小时、未来30天内；确认资格10分钟、审批30分钟，二者均不晚于开始时间。签到在开始前10分钟到开始后15分钟内，开始后15分钟边界不再允许；还要求尚未到结束时间。结束时间和起止的严格比较应直接读 `checkIn/maintain/validateTimes`。

不要只记“超时有定时任务”：`accept/decide`在锁内再次检查截止时间，即使调度暂时未跑，迟到请求也不能绕过期限。状态清理由后续维护完成。

终态幂等不是所有动作都一样：取消已取消、完成已完成等明确支持重放；不意味着任意状态都返回成功。阅读测试比概括“所有接口幂等”更准确。

## 7. 并发、事务、锁与幂等

### 7.1 为什么不能只先查再写

事务T1和T2同时查询“没有重叠”，之后都插入，就会超卖。普通SELECT在READ_COMMITTED下不会替你串行化业务检查。

当前先锁equipment行，使同设备的判断、状态变更与候补决策串行；时隙主键作为最后约束。两个事务同时请求同一设备：T1先得到锁并提交，T2锁到后看到最新占用，正常进入候补。

### 7.2 为什么同时需要用户锁

设备锁只能保护一台设备。一个用户同时预约不同设备，两个事务可能都看到49条活跃记录，然后各自插入，超过50条；跨设备复用同一requestKey也需要一致判断。因此创建类路径先锁用户再锁设备。

锁顺序是**用户行→设备行**。取消、确认、审批等只锁设备，不再反向拿用户锁。统一顺序降低死锁风险，不等于所有SQL永远不会死锁；新增多设备操作、索引和其他事务都可能引入新锁路径。

### 7.3 事务边界与Spring代理

`BookingService`类使用 `@Transactional(isolation = READ_COMMITTED)`，由Spring代理开启事务。预约、分配、审计和事件共用它。抛出未捕获的运行时异常会回滚。

`reschedule`内部直接调用 `create`，不会因为自调用重新触发代理；这里依赖的是已经存在的外层事务，所以旧单取消、新单创建和关联记录仍在一笔事务内。不要误答成“每次方法调用都会自动开启新事务”。

`OutboxDispatcher`没有包住整批事件的业务事务，而是调用另一个Bean `OutboxDelivery.deliver`。它经代理为每个事件建立独立事务，一条坏事件不会让前面已提交的正常通知全回滚。

### 7.4 READ_COMMITTED解决什么

它提供已提交数据可见性，不自动防止本业务的所有并发异常。资源排他依靠设备锁，配额依靠用户锁，最终冲突依靠主键；状态条件更新再防止错误覆盖。

将隔离级别改为SERIALIZABLE不是免费升级：可能扩大锁范围和等待，还需要理解候补、幂等与业务错误语义。项目选择较明确的显式锁边界。

### 7.5 三种锁/约束的区别

| 手段 | 当前用途 | 不能替代什么 |
| --- | --- | --- |
| 数据库唯一约束 | 不允许同设备同槽双占、同事件双通知 | 不负责公平候补与配额判断 |
| SELECT FOR UPDATE行锁 | 保护检查与多表状态变更 | 需要事务与一致锁顺序 |
| version乐观版本 | 防管理员基于旧页面覆盖设备启用状态 | 不代替预约时段串行分配 |
| Redis分布式锁 | 当前未使用 | 不应为简历虚构；引入后仍需数据库最终约束 |

### 7.6 幂等不只是“查到就返回”

创建幂等键范围是同一用户；重放时核对设备、开始、结束和trim后的用途。同键同参数返回原预约，即使它后来取消或时间已过去；同键异参数409。先重放再做当前时间校验，避免合法重试被“已过期”拒绝。

改期有独立关联记录，核对源预约与目标时间，返回同一替代预约。不要拿一个新键无限重复业务操作，幂等只约束同一个逻辑请求。

## 8. 候补公平与多实例调度

### 8.1 公平是重叠范围内的FIFO

设备15:00—16:00已占用；较早候补A要14:00—17:00，较晚B只要14:00—15:00。虽然B所需槽当前空闲，仍需等待，避免B不断插队导致A饥饿。不重叠的18:00—19:00请求可以分配。

这会牺牲部分即时利用率。面试应主动说明这是产品取舍，不要同时声称“严格公平”和“利用率最优”。

### 8.2 maintain到底做什么

先处理到期维修、确认/审批超时、开始已到的候补、未签到与使用到期；再读取占用槽与资格集合，按预约ID顺序处理候补。可分配时先插槽并变更OFFERED，同事务提交。

无法分配的前序等待区间合并到有序区间集合，后来的重叠区间受阻。这避免为每条候补反复扫描完整前序队列，也减少逐条查槽/资格的SQL；仍然在同设备锁内，长队列依旧增加锁持有时间。

### 8.3 多实例怎样避免重复分配

两个实例可以同时发现同一设备需要维护。实例A先锁设备并晋升候补；B等待后重读已提交状态，不会再把同一候补分配一次。`change`通过 `WHERE id=? AND status=?` 条件更新，异常状态不会被无条件覆盖。

这是**允许重复调用、保证业务效果一致**，不是“分布式任务绝对只执行一次”。`synchronized tick`仅限制单进程内重入；跨进程正确性来自数据库。

### 8.4 调度分页和延迟

`Store.dueEquipment`找出有候补、到期确认/审批、未签到、使用到期或维修结束的设备；`Maintenance.tick`使用设备ID游标，每轮最多100台，扫完后回到起点。失败设备会在后续循环再遇到。

默认维护固定延迟5秒，通知固定延迟500ms，调度池2线程。fixedDelay从上次结束后计算；扫描、锁等待、批次积压都会增加实际延迟。因此不能承诺“5秒内严格回收”。

## 9. 审批、资格、维修与改期

审批中占槽，否则批准时才发现被别人抢走，会出现产品语义冲突。占槽成本由审批截止时间控制；拒绝或超时释放后再维护候补。

培训授予/撤销需要管理员；撤销只影响该用户该设备的有效申请，正在使用时拒绝撤销。没有资格有效期和培训申请流，不要讲成完整培训系统。

设备停用会取消尚未使用的有效申请和候补；有IN_USE时拒绝停用。设备version避免管理员A覆盖管理员B已经修改的状态。普通用户不能通过前端隐藏字段绕过服务端角色校验。

维修和预约共用时隙主键空间。创建维修前检查重叠有效申请，包括候补，不静默取消别人；取消或到期释放维修槽，保留设备审计。

原子改期：锁用户、查改期幂等、锁设备、验证原单和目标→取消旧单→创建替代单→写关联。目标有占用、候补或维修则拒绝；任何写入失败整笔回滚，原单和原槽恢复。新时段仍需满足当前培训/审批要求。

为什么不直接UPDATE原单日期？保留原请求参数、历史审计和创建幂等语义更清晰。代价是多一条新预约与关联表，需要界面解释原单因改期而取消。

## 10. Outbox、通知与故障恢复

### 10.1 两个原子边界

```text
事务A：reservation变更 + slot变更 + audit + event_outbox
事务B：锁定单个outbox事件 + 写inbox + 标记delivered_at
```

事件候选查询可以被多个投递器同时看到，但 `deliver` 在事务内锁事件并重新检查是否已投递/失败/到重试时间；Inbox的event_id唯一再提供兜底。

### 10.2 故障矩阵

| 崩溃点 | 数据结果 | 恢复方式 |
| --- | --- | --- |
| 业务事务提交前 | 业务、槽、审计、事件一起回滚 | 客户端按同一requestKey重试 |
| 业务已提交，响应丢失 | 原预约和事件存在 | 同键返回原结果，不再创建一单 |
| 业务提交后、通知投递前 | Outbox待投递 | 调度器重启后继续扫描 |
| Inbox已写但投递事务未提交 | Inbox和确认一起回滚 | 后续重新投递 |
| 投递事务已提交、调度器未返回 | Inbox与确认都已存在 | 重复调用直接跳过 |
| 某事件持续失败 | 记录重试/退避，最终隔离 | 修复原因，管理员审计重试 |
| 应用停机期间审批/候补过期 | 期限仍在数据库 | 重启后维护判断现在时间并推进状态 |

### 10.3 退避要按代码讲准确

失败次数count加1，延迟按 `min(300, 2^min(count,8))` 秒计算，五次失败后写failed_at隔离。因为当前第五次就隔离，不能说“正常会一路重试到300秒”：前几次实际是2、4、8、16秒等待，第五次已经停止自动投递。管理员重试会清除失败状态并写重试审计。

Outbox不是无条件“Exactly-once”。本项目在同一个数据库中，通过事务和唯一键实现站内通知一次可见效果；未来接入MQ/邮件时，数据库提交与外部发送无法共用这个本地事务，还需要接收方幂等、消息ID、确认与补偿。

## 11. 身份、时间与接口契约

### 身份

- 注册只能得到USER，不能通过JSON传role变成管理员。
- BCrypt存密码哈希，输入UTF-8最多72字节，字符数和字节数不是一回事。
- Token为32字节安全随机数，返回客户端；数据库保存SHA-256摘要，有效期12小时，退出删除会话。
- 随机高熵token适合快速摘要查找；用户密码低熵，需要慢密码哈希。不要混淆这两种哈希用途。
- 登录节流是按用户名的实例内辅助限制，不能冒充集群级限流。公开部署还需要HTTPS、真实账号治理和网关防护。

### 时间

数据库以UTC约定存LocalDateTime，响应显式带Z；带偏移输入先归一到UTC，无偏移输入沿用UTC约定。`10:00+08:00`与`02:00Z`应命中同一时隙和同一幂等参数。查询字符串中的加号要URL编码成 `%2B`。

业务Clock可注入，测试用MutableClock直接推进时间，不靠sleep等十几分钟。数据库时间、JVM时间、API偏移和浏览器本地显示是不同层，必须形成统一约定。

### 接口

400输入错误、401未登录、403角色或归属不符、404不存在、409业务冲突、405方法不支持、415Content-Type错误。不要把这些都返回200或500。

公开时段查询只返回槽时间与占用种类，不泄露别人的用户ID/用途/预约ID。管理员运行信息在受保护的管理接口，Actuator公共入口只开放health。

### 12.2 五个建议亲手完成的实验

### 12.3 排障路径

| 现象 | 优先检查 |
| --- | --- |
| 启动报Flyway校验失败 | 是否修改旧迁移、是否连错库；不要直接repair掩盖差异 |
| 重启数据没了 | 工作目录是否变更、是否用了另一H2文件或内存URL |
| 候补一直不晋升 | 设备启用、培训、前序重叠候补、占用槽、deadline、调度日志 |
| 通知没收到 | Outbox是否提交、next_attempt_at、failed_at、Inbox及管理员运行概览 |
| 改期409 | 本人/CONFIRMED/未开始、目标候补/维修/占用、重复键参数 |
| 性能突然变差 | 热设备锁等待、事务耗时、连接池等待、DB CPU/IO与索引，而非先扩线程 |
| 页面时间差8小时 | 请求是否带偏移、数据库约定、查询加号编码、浏览器显示 |

在独立测试库可执行只读核验SQL：

```sql
-- 终态预约不应仍然占槽；结果应为0。
SELECT COUNT(*) FROM reservation_slot s JOIN reservation r ON r.id=s.reservation_id
WHERE r.status IN ('COMPLETED','CANCELLED','REJECTED','EXPIRED','NO_SHOW');

-- 数据库主键/唯一键已约束，额外检查可用于导入/恢复后的核验。
SELECT event_id,COUNT(*) FROM inbox_notification GROUP BY event_id HAVING COUNT(*)>1;

SELECT COUNT(*) AS pending FROM event_outbox
WHERE delivered_at IS NULL AND failed_at IS NULL;
SELECT id,retry_count,next_attempt_at,last_error FROM event_outbox
WHERE delivered_at IS NULL ORDER BY id LIMIT 20;
```

不要用“槽总数必须等于活跃预约数”验收：一个预约占多个槽，WAITLISTED不占槽，维修也占槽。

## 13. 性能、演进与生产边界

### 13.1 当前取舍

同设备写操作串行，越热门越容易等待；不同设备可并行，但同一用户创建仍共享用户行锁。减少无关SQL和事务持锁时间通常比盲目扩大线程池更有价值。

半小时时隙模型的优点是排他约束简单、冲突检测易验证；缺点是粒度固定、长预约多行。如果改为任意分钟区间，需要重做区间约束方案，不能只删除整半点校验。

### 13.2 如果面试官要求扩展

| 要求 | 可讨论方案 | 当前是否已实现 |
| --- | --- | --- |
| 多设备原子预约 | 先锁用户，设备ID排序加锁，全部分配或整体回滚；测试死锁与重试 | 否 |
| 任意区间 | 设备锁内判断 `start<otherEnd && end>otherStart`，评估索引与最终约束 | 否 |
| 更高热点吞吐 | 测锁持有时间，分离只读查询、缩短事务；按设备串行队列需持久化和恢复 | 否 |
| 外部MQ通知 | Outbox发送、消息ID、接收幂等、ack与重试 | 否 |
| 培训有效期 | 资格有效截止、创建/确认/签到时语义、已批准预约处理策略 | 否 |
| 规则版本变更 | 明确新旧申请采用哪一版、审计版本、不可静默改已批准结果 | 否 |
| 真实设备控制 | 门禁/设备状态、超时和人工处置，不能把软件完成当作物理停止 | 否 |

这些是设计题，不要以“我实现了……”开头。优先根据真实反馈选一项，不需要同时扩展。

### 13.3 负载数字怎样讲

说清硬件、数据库版本、实例数、客户端数、热点设备数、时长、请求组成、成功/冲突/错误分类、p50/p95和结束后数据不变量。历史30秒样本只说明那次限定场景，不代表极限QPS、长期稳定性或生产承诺。

### 30秒版本

### 90秒版本

“设备预约的库存是资源加时间区间，还有培训、审批和候补规则。我选择半小时时隙，将设备与时间设为联合主键；创建先锁用户保证跨设备配额和幂等，再锁设备串行化分配。冲突进入候补，较早重叠候补不能被后来短请求绕过；OFFERED和审批中都会占位，但期限持久化，到期可重复维护。

改期不是直接改原单，而是在同一事务取消旧单、创建关联新单，失败整体回滚。业务、审计和Outbox一起提交，通知按单事件事务写Inbox和确认，失败退避并隔离。测试覆盖竞争、回滚和时间边界，当前49项在H2和MySQL通过。代价是同设备串行、固定时间粒度，尚未接真实学校身份和硬件。”

### 五分钟深挖顺序

业务目标30秒→数据不变量45秒→并发双事务推演90秒→候补公平45秒→故障矩阵45秒→测试证据与边界45秒。不要先花三分钟介绍Spring注解。

### 高频追问：先直接回答，再给证据

**1. 为什么不用Redis锁？** 当前所有关键状态都在一个数据库，行锁与本地事务更容易统一原子边界。增加Redis锁还要处理租约失效和双写，仍不能省掉最终数据库约束。

**2. 有主键还要设备锁吗？** 主键守住双占，但公平候补、审批状态、配额等多步判断仍需要一致视图。不能把正常业务竞争全变成唯一键异常。

**3. 为什么不是只锁设备？** 同用户跨设备配额和幂等键需要用户锁。用49条额度并发创建两台设备的例子说明。

**4. 为什么乐观锁不解决所有问题？** version适合防管理员旧页面覆盖；预约还涉及多槽插入、候补决策和多表事务，用设备锁更直接。

**5. 同设备串行不慢吗？** 是取舍。实验室单件设备竞争需要确定顺序；先测锁竞争和事务耗时，再考虑更复杂队列。当前不承诺互联网秒杀吞吐。

**6. 预约时间怎么判断重叠？** 半开区间满足 `a.start < b.end && a.end > b.start`。实际最终占用以半小时时隙主键约束。

**7. 长候补挡住短候补会浪费资源吗？** 会，但避免长预约饥饿；不重叠请求仍能进行。这是公平与利用率的明确取舍。

**8. 为什么候补要确认？** 自动给用户安排可能已不符合其需求，限时资格允许用户确认；代价是暂时占位，通过截止时间回收。

**9. 两个定时任务同时处理怎么办？** 设备锁+锁后重读+条件更新，允许重复扫描但不重复产生业务效果。实例内synchronized不是分布式保证。

**10. 服务停一小时会丢任务吗？** 状态和deadline在数据库；恢复后按当前时间推进。不会补发每一个错过的tick，而是恢复应有状态。

**11. 取消与审批同时发生谁赢？** 都通过同设备锁串行，后到者重读状态；已取消不能被迟到审批复活。对应有竞争回归测试。

**12. 为什么改期创建新单？** 原请求和历史语义保持稳定，新目标重新校验/审批。外层事务确保旧单取消和新单创建一起提交。

**13. Outbox解决什么？** 业务提交与待通知事件同时落库，避免业务成功却没有发送记录；投递可恢复。当前只实现同库站内通知，不是跨服务消息一致性全套方案。

**14. 消息重复怎么办？** 锁内重查投递状态、Inbox event_id唯一、写入和确认同事务。外部消费者则还要有自己的幂等机制。

**15. 一条坏消息会影响整批吗？** deliver经另一个Bean代理，每事件独立事务；失败记录退避与隔离，正常事件可以继续。

**16. 能保证Exactly-once吗？** 不笼统保证。能说明本地事务边界与唯一键下的数据库可见效果；网络、外部邮件/MQ不在此保证范围。

**17. 为什么token不直接存库？** 随机token泄露会获得会话权限，存摘要降低数据库泄露后的直接滥用；仍要HTTPS、到期与撤销。不是说存摘要就解决所有安全问题。

**18. 怎样证明你真的做过？** 现场跑场景、指出测试断言、解释一次真实失败及修复。比如偏移时间原请求400，修复统一UTC解析后等价时间重放和冲突测试通过。

**19. 项目最大的不足？** 缺真实试用与部署反馈，固定粒度和单设备范围，生产账号治理/备份还需补齐。给出按价值排序的下一步，而不是泛称“高并发优化”。

**20. 为什么适合作为研究生项目？** 场景贴近实验室、规则可理解且可找同学验证；深度来自竞争、状态与故障边界，不来自项目名字。

### 不会的问题如何回答

“当前实现是A，保证范围是B；你问的C没有实现。我会先确认X，再比较方案Y/Z，并用失败场景T验证。”这比猜测系统已经具备某项能力更可信。

## 16. 新增客户端与调度延迟补充（2026-10-23）

项目现在包含响应式网页和原生微信小程序源码。先阅读 [小程序完整入门与联调手册](MINIPROGRAM-GUIDE.md)，再从 `miniprogram/utils/api.js` 追到 `ApiController`。两端复用同一个用户、设备、预约状态和数据库锁；小程序主要面向预约用户，管理动作仍在网页完成。

本轮补充了“调度器延迟时下一用户签到”的边界：`checkIn` 在设备行锁内，将已到结束时间的前一 `IN_USE` 预约转换为 `COMPLETED`，然后检查是否还有有效使用者。结束时间之前仍拒绝下一人提前签到，防止两个有效使用者同时占用设备。状态变化、槽释放、审计、Outbox 仍在同一事务内。后台扫描负责最终清理，前台操作也维护自身所需的不变量。

面试追问：“为什么已经有定时任务，还要在签到里处理？”答：定时任务有调度间隔，也可能停顿；请求路径不能把到期占用的及时释放完全依赖于后台任务。两者使用相同设备锁和状态转换，保证并发执行时不会重复分配。注意“到期自动完成”是当前业务规则，不能据此证明物理设备已经空闲；真实实验室可升级为设备遥测确认、超时告警和管理员接管。
